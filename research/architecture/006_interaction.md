## 문제

플레이어가 NPC에게 말 걸고, 아이템을 줍고, 문을 열려면 각각 다른 코드가 필요해 보인다. 그러나 그렇게 만들면 플레이어 코드가 "이건 NPC인가? 아이템인가? 문인가?"를 일일이 확인하게 되고, 새 종류가 생길 때마다 플레이어 코드를 고쳐야 한다. 쉽게 말해: 문 손잡이 모양이 제각각이어도 우리는 "돌리면 열린다"는 약속만 알면 된다. IInteractable이 그 손잡이 약속이다.

## 구조

- 위치: `Assets/Scripts/Interaction/` — IInteractable 인터페이스, Trigger 기반. [출처: reference/unity_project_baseline.md 기준 구조]
- 약속(인터페이스): 상호작용 가능한 모든 대상이 지키는 최소 규격. 상호작용 실행 함수 하나와, 화면에 띄울 안내 문구(예: "대화하기") 정도만 노출한다.
- 감지: 대상에 Trigger로 설정한 2D 콜라이더를 두고, 플레이어가 범위에 들어오면 후보로 등록·나가면 해제한다.
- 실행: 플레이어가 상호작용 키를 누르면 → 현재 후보 중 하나를 골라 → 약속된 실행 함수를 부른다. 플레이어는 대상이 NPC인지 상자인지 모른다.
- 결과 방송: 실행 결과(대화, 획득 등)는 ARCH-001 이벤트 버스로 방송된다.

## 핵심 규칙

- 플레이어 코드는 구체 타입을 알지 않는다. 타입 검사로 분기하는 순간 이 구조의 존재 이유가 사라진다.
- 상호작용 결과 사건(대화, 획득)은 반드시 방송한다. [출처: reference/unity_project_baseline.md 방송 규칙]
- 상호작용 대상은 청크 씬에 속한다. 후보 목록은 대상이 파괴되거나 청크가 꺼질 때 반드시 정리한다. 정리하지 않으면 사라진 대상을 부르다 터진다.
- 후보가 여럿일 때 선택 규칙을 하나로 정한다(예: 가장 가까운 것). 규칙이 없으면 프레임마다 대상이 바뀌어 플레이어가 혼란스러워한다.
- 상호작용 실행 함수는 짧게 유지한다. 실제 내용(대화 진행, 인벤토리 추가)은 각 시스템에 위임한다.

## Unity 구현 절차

1. `Scripts/Interaction/IInteractable.cs` 생성 — 실행 함수와 안내 문구만 담은 최소 약속.
2. `Scripts/Interaction/InteractionDetector.cs` 생성 — 플레이어에 붙는 감지기. Trigger 진입/이탈 콜백에서 후보를 등록·해제한다.
3. 후보 선택 규칙 구현 — 가장 가까운 후보를 고르고, 그 대상의 안내 문구를 UI에 전달한다.
4. 입력 연결 — PlayerInput에서 상호작용 키를 받아 선택된 후보의 실행 함수를 호출한다.
5. 대상 구현 — NPC(대화, ARCH-005의 Talk 전이 요청), 아이템(획득), 문(열기)이 각각 약속을 구현한다.
6. 방송 연결 — 실행 성공 시 이벤트 버스로 사건을 알린다.
7. 정리 처리 — 대상이 비활성/파괴될 때 후보 목록에서 자신을 빼는 경로를 만든다.

## 안티패턴

- 타입 분기: 플레이어 코드에서 대상 종류를 확인해 갈라지는 방식. 종류가 늘 때마다 플레이어를 수정해야 하고, 결국 아무도 못 고치는 함수가 된다.
- 이름·태그로 판별: 오브젝트 이름이나 태그 문자열로 대상을 구분하는 방식. 오타 한 글자에 조용히 실패하며 컴파일러가 잡아주지 못한다.
- 상호작용 함수에 모든 로직 몰기: 실행 함수 안에 대화 UI 조작, 인벤토리 처리, 사운드까지 넣는 방식. 인터페이스가 얇아야 유지된다.
- 후보 정리 누락: 파괴된 대상이 후보로 남는 문제. 청크가 자주 꺼지는 이 프로젝트에서는 특히 자주 발생한다.
- Trigger 범위 과대: 감지 범위를 넓게 잡아 여러 대상이 동시에 잡히는 상태. 플레이어가 무엇과 상호작용할지 예측할 수 없어진다.

## 검증 방법

- 컴파일 에러 0개, 콘솔 에러 0개. [출처: reference/unity_project_baseline.md 자체 점검 기준]
- 다형성 검사: NPC·아이템·문 세 종류를 각각 상호작용했을 때 플레이어 코드 수정 없이 동작해야 한다.
- 방송 검사: 대화·획득 상호작용 후 `Logs/commentator.log`에 해당 이벤트 줄이 남아야 한다. [출처: reference/unity_project_baseline.md 로그 규칙]
- 정리 검사: 상호작용 범위 안에서 대상을 파괴하거나 청크를 언로드한 뒤 상호작용 키를 눌러도 에러가 없어야 한다.
- 선택 규칙 검사: 두 대상 사이에 섰을 때 항상 같은 규칙(가까운 쪽)으로 선택되어야 한다.
- UI 검사: 범위 진입 시 안내 문구가 뜨고, 이탈 시 사라져야 한다.

## 조합 궁합

- ARCH-005 (NPC 상태머신): 대화 상호작용이 Talk 상태 전이를 요청하는 관계.
- ARCH-001 (이벤트 버스): 상호작용 결과 방송 경로.
- ARCH-002 (씬 스트리밍): 대상이 청크에 속하므로 후보 정리 규칙이 여기서 나온다.
- ELEM-011 (창발적 시스템 상호작용): 궁합 주의 — 오브젝트끼리 서로 반응하는 설계로 가면 "플레이어가 누른다"는 이 구조만으로는 부족하고, 오브젝트 간 상호작용 채널이 따로 필요하다.
- ELEM-012 (랜드마크 기반 탐험): 궁합 좋음 — 마커 없이 탐험하게 하려면 "가까이 가면 안내가 뜬다"는 이 구조가 발견의 보상 역할을 한다.
