## 문제

NPC 행동을 if 문으로 만들면 조건이 늘 때마다 분기가 얽혀 아무도 손댈 수 없는 코드가 된다. "가만히 있다가, 플레이어가 오면 말을 걸고, 아니면 순찰한다"는 간단한 규칙조차 몇 번만 확장하면 어떤 상황에서 무엇이 실행되는지 추적이 불가능해진다. 쉽게 말해: 신호등은 빨강·노랑·초록 중 딱 하나만 켜진다. 그래서 지금 무슨 상태인지 누구나 안다. NPC도 그렇게 만들면 된다.

## 구조

- 위치: `Assets/Scripts/NPC/` — 상태머신(Idle / Patrol / Talk). [출처: prompts/5_developer.md 기준 구조]
- 구성 요소 3가지: ① 상태들(각 상태가 자기 행동을 안다) ② 현재 상태를 하나만 들고 있는 문맥(NPC 본체) ③ 전이 규칙(언제 어느 상태로 옮기는가).
- 상태별 3개 지점: 들어올 때(Enter), 머무는 동안(Update), 나갈 때(Exit). 나갈 때 정리를 빼먹는 것이 버그의 단골 원인이다.
- 기본 상태 3종 — Idle(제자리 대기), Patrol(정해진 경로 왕복), Talk(플레이어와 대화). 전이 예: Idle → (시간 경과) → Patrol, Patrol/Idle → (상호작용 발생) → Talk, Talk → (대화 종료) → Idle.
- 구현 형태는 상태별 클래스 분리 방식과 열거형 + switch 방식이 있다. 상태가 셋 정도면 후자로 시작해도 되고, 늘어나면 전자로 옮긴다. [해석] 이 프로젝트는 상태가 늘어날 가능성이 높으므로 처음부터 클래스 분리가 안전하다.

## 핵심 규칙

- 동시에 활성 상태는 하나뿐이다. "대기하면서 순찰하는" 상태는 없다. 필요하면 새 상태를 만든다.
- 전이 조건은 한곳에 모은다. 상태 안에서 제멋대로 다른 상태로 뛰면 흐름을 읽을 수 없다.
- 대화(Talk) 진입은 방송한다. 플레이어의 대화는 방송 규칙 대상 행동이다. [출처: prompts/5_developer.md 방송 규칙]
- NPC는 청크 씬에 속한다. 언제든 언로드될 수 있으므로 상태머신은 씬 밖 객체를 직접 참조하지 않는다. [출처: prompts/5_developer.md 청크 규칙]
- 상태 이름은 행동을 뜻하는 단어로만 짓는다. TempState, State2 같은 이름 금지 — 이름이 곧 문서다.

## Unity 구현 절차

1. `Scripts/NPC/INpcState.cs` 생성 — Enter / Update / Exit 세 개의 약속만 정의한다.
2. `Scripts/NPC/States/` 하위에 IdleState, PatrolState, TalkState 각각 생성.
3. `Scripts/NPC/NpcController.cs` 생성 — 현재 상태 보관, 매 프레임 현재 상태의 Update 호출, 상태 교체 함수(이전 상태 Exit → 새 상태 Enter) 제공.
4. 전이 규칙 배치 — NpcController에 조건 검사를 모으고, 조건 충족 시에만 교체 함수를 부른다.
5. Patrol 경로는 데이터로 둔다 — 순찰 지점을 코드에 박지 말고 인스펙터에서 지정하거나 `Data/`에 둔다. 기획 변경 때 코드를 안 고쳐도 되게 한다.
6. Talk 연동 — ARCH-006 상호작용에서 대화 요청을 받아 Talk로 전이하고, 이벤트 버스로 대화 사건을 방송한다.
7. 물리 이동이 필요한 Patrol은 ARCH-009의 규칙을 따른다(직접 좌표 대입 금지).

## 안티패턴

- 거대 if 덩어리: Update 안에 조건문을 계속 덧붙이는 방식. 상태머신을 쓰는 이유 자체가 이걸 피하기 위해서다.
- 상태 플래그 남발: isIdle, isTalking, isPatrolling 같은 불리언을 여러 개 두는 방식. 동시에 두 개가 참이 되는 순간 아무도 원인을 못 찾는다. 상태는 하나의 값으로 표현한다.
- Exit 정리 누락: 상태를 나가면서 코루틴·구독·애니메이션을 정리하지 않아, 다음 상태에서 유령처럼 이전 행동이 남는 현상.
- 상태 안에서 직접 상태 교체: A 상태 Update에서 곧바로 B로 갈아타고, B가 다시 A로 돌아오는 순환. 같은 프레임에 전이가 반복되면 게임이 멈춘다. 전이는 프레임당 한 번으로 제한한다.
- 상태머신에 대사 내용 넣기: 상태는 "무엇을 하는가"이고 대사는 데이터다. 대사를 상태 코드에 넣으면 기획 변경마다 코드 수정이 필요하다.

## 검증 방법

- 컴파일 에러 0개, 콘솔 에러 0개. [출처: prompts/5_developer.md 자체 점검 기준]
- 단일 상태 검사: 어느 시점에나 NPC의 현재 상태 값이 정확히 하나여야 한다.
- 전이 검사: 플레이어가 접근해 대화를 시작하면 Talk로, 종료하면 Idle로 돌아와야 한다. 돌아오지 않으면 Exit 처리 누락이다.
- 방송 검사: 대화 시작 시 `Logs/commentator.log`에 대화 이벤트 줄이 남아야 한다. [출처: prompts/5_developer.md 로그 규칙]
- 청크 안전성 검사: NPC가 있는 청크를 언로드해도 콘솔 에러가 나지 않아야 한다.
- 순찰 검사: Patrol 상태에서 지정한 경로 지점을 순서대로 지나야 한다.

## 조합 궁합

- ARCH-006 (상호작용): Talk 상태로 들어가는 입구. 상호작용이 요청하고 상태머신이 수행한다.
- ARCH-001 (이벤트 버스): 대화 사건 방송 경로.
- ARCH-009 (2D 물리 이동): Patrol의 실제 이동 방식은 이 카드의 규칙을 따른다.
- ELEM-005 (AI 통합): 궁합 주의 — 대사를 AI가 실시간 생성하는 설계로 가면 Talk 상태가 "응답 대기" 시간을 갖게 된다. 대기 중 플레이어가 떠나는 경우의 전이를 반드시 설계해야 한다.
- ELEM-008 (동반자 / 함께 플레이 가능한 캐릭터): 궁합 좋음 — 동반자도 같은 상태머신 구조를 재사용할 수 있다(Follow 상태 추가).
