## 문제
싱글플레이 게임이라 해도 온라인 랭킹·도전 과제·리더보드가 있다면, 플레이어가 세이브
파일을 손으로 고쳐 "1시간 만에 클리어했다"고 거짓 기록을 남길 수 있다. 이는 정직한
플레이어의 성취감을 무너뜨린다.

## 구조
- 기준 형식: 세이브 데이터는 평문이 아니라 게임 고유 키로 암호화된 바이너리 또는
  해시(checksum) 추가 저장 [출처: 게임 개발 표준, prompts/5_developer.md 기준]
- 검증 흐름: 로드 시 저장된 해시와 현재 파일의 해시를 비교해 일치하지 않으면 거부
  [출처: 보안 규칙, 5_developer.md 기준]

## 핵심 규칙
- 암호화 키는 소스 코드에 하드코딩하지 않는다 (컴파일된 바이너리로도 추출 가능).
  대신 서버에서 플레이 세션마다 발급받거나, 게임 내부 상수로 매 빌드마다 재생성.
- 멀티플레이/온라인 기능이 없는 게임이더라도, 나중에 랭킹 추가 시 기존 세이브가
  부정으로 낙인 찍히지 않도록 미리 규약을 정해두는 것이 좋다.
- 접근성: 싱글 플레이 전용이면 "이 게임은 평문 저장 (조작 가능)" 공시가 정직하다.

## Unity 구현 절차
1. `PlayerPrefs` 대신 암호화 라이브러리(예: AES) 사용.
2. 세이브 데이터: `{encrypted_data + checksum}` 형태로 저장.
3. 로드 시: checksum 재계산 → 저장된 값과 비교 → 불일치 시 `LoadFailed` 이벤트.
4. 서버 기능 추가 시: 업로드 전 클라이언트에서 서명(signing) 단계 추가.

## 안티패턴
- 암호화 없이 JSON 저장: 텍스트 에디터로 직접 수정 가능.
- 클라이언트가 자신의 점수를 서버에 전송하고 검증 없이 저장: 조작 가능.
- 매번 다른 키로 암호화: 키 관리 복잡도 상승, 실수로 인한 관통 위험.

## 검증 방법
- 형식 검사: 세이브 파일 로드 실패율이 0이어야 함 (정상 게임오버 제외).
- 보안 검사: 저장 파일을 바이너리 에디터로 수정 후 로드 시도 → 거부돼야 함.
- 콘솔 청결: 체팅 시도 로그 기록 (로그 규약 ARCH-010 참조).

## 조합 궁합
- ELEM-003 (제4의 벽 붕괴): 메타 내러티브에서 "플레이어가 저장을 조작했다"는 게임의
  자각이 스토리의 일부가 될 때, 이 규약이 실제 부정행위 탐지 도구로 기능한다.
- [해석] 싱글 게임에서 세이브 조작은 사실상 방지 불가능하며, 목표는 "불가능"이
  아니라 "정직한 플레이어의 신뢰 유지"다.
