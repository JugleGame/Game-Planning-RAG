## Problem
게임은 시작 화면에서 플레이로, 플레이에서 결과 화면으로 넘어간다. 이 넘어가는 일을 아무
스크립트나 직접 하면, "지금 어디서 어디로 갈 수 있는가"라는 게임의 뼈대가 코드 곳곳에
흩어져 아무도 전체를 볼 수 없게 된다. 건물에 계단이 여러 개 몰래 나 있는 것과 같다.
계단을 한 곳에 모으고, 그 계단으로만 다니게 만드는 것이 이 구조다.

## Structure
- 흐름 담당자는 하나다. 씬을 바꾸는 요청은 전부 이 한 곳을 지나며, 다른 스크립트는 "다음
  단계로 가 달라"고 말할 뿐 어느 씬인지 알지 못한다.
- 기본 경로: Boot(매니저 생성) → 타이틀 → 플레이(World_Base + Chunk) → 결과 → 타이틀.
  플레이 구간에서 상시 씬 World_Base는 유지한 채 Chunk 조각만 켜고 끈다 [source: reference/unity_project_baseline.md 3절 기준 구조].
- 흐름과 상태는 다른 것이다. 지금이 진행 중인지 멈춤인지 끝인지는 GameManager(ARCH-018)가
  들고 있고, 그 상태가 바뀔 때 어느 씬으로 이동할지는 이 구조가 정한다.
- 매니저는 Boot에서 한 번만 만들어지고 이후 전이에서 다시 만들어지지 않는다(ARCH-011).
- [interpretation] 그래서 전이 표는 "씬 이름 목록"이 아니라 "허용된 이동의 목록"이다. 목록에 없는
  이동은 코드가 아니라 표가 막는다.

## Core Rules
- 씬 로딩 API를 흐름 담당자 밖에서 직접 부르지 않는다. 한 곳에 모여 있지 않으면 전이 표가
  진실이 아니게 된다.
- 전이는 비동기로 한다. 동기 로딩은 로딩이 끝날 때까지 화면이 멈춘다.
- 로딩 중에는 입력을 받지 않는다. 전이 요청이 두 번 겹치면 어느 씬이 살아남는지 예측할 수
  없다.
- 미리 읽어두고 나중에 보여줘야 할 때는 씬 활성화를 꺼둔다. 이 경우 진행률은 0.9에서 멈춘
  채 대기하고, 활성화를 다시 켜야 완료된다 [source: Unity 스크립팅 API AsyncOperation.allowSceneActivation, 2026-08 확인].
- 상시 씬(World_Base)은 언로드 대상이 아니다. 언로드하면 플레이어·카메라·UI가 함께 사라진다.
- 결과 화면은 점수를 다시 계산하지 않는다. 이미 확정된 상태를 받아 보여주기만 한다.

## Unity Implementation Steps
1. 씬을 빌드 대상 목록에 등록한다. 등록되지 않은 씬은 에디터에서만 열린다.
2. 허용된 전이를 한 곳에 표로 적는다. 여기가 이 구조의 실체이고 나머지는 그 표를 실행하는
   코드다.
3. 전이 요청 창구를 하나만 노출한다. 다른 시스템은 이 창구만 알고 씬 이름은 모른다.
4. 비동기 로딩을 걸고 진행률로 로딩 화면을 갱신한다. 즉시 보여줄 필요가 없으면 활성화를
   꺼둔 채 대기시킨다.
5. 새 씬이 준비된 뒤 이전 씬을 언로드한다. 덧붙여 로딩(Additive)한 씬은 스스로 정리되지
   않으므로 언로드를 빠뜨리면 메모리에 남는다 [source: Unity 스크립팅 API SceneManager.UnloadSceneAsync, 2026-08 확인].
6. 전이가 끝나면 완료를 방송한다(ARCH-001). 각 시스템은 이 방송을 듣고 스스로 초기화한다 —
   흐름 담당자가 개별 시스템을 하나씩 부르기 시작하면 다시 거미줄이 된다.
7. 전이 한 건마다 로그를 한 줄 남긴다(ARCH-010). 전이는 눈으로만 확인하기 어려운 사건이다.

## Anti-patterns
- 아무 스크립트에서나 씬 로딩 호출: 흐름 표와 실제 동작이 갈라지고, 되돌아가는 경로가 생겨도
  아무도 모른다.
- 동기 로딩: 로딩 동안 화면이 멎어 사용자에게는 멈춘 게임으로 보인다.
- Boot을 건너뛰고 플레이 씬을 직접 실행: 매니저가 없는 상태로 시작해 곳곳에서 참조 오류가
  난다. 에디터에서만 재현되는 가장 흔한 함정이다 [source: mortoray.com 'Loading a bootstrap scene while testing in the Unity editor', 2026-08 확인].
- 결과 화면에서 상태 재계산: GameManager가 상태의 유일한 소유자라는 전제가 깨지고, 두 곳의
  숫자가 어긋나기 시작한다.
- 전이 때마다 매니저 재생성: 씬을 오갈수록 같은 매니저가 여러 개 쌓인다.

## Verification
- 순회 검사: 타이틀 → 플레이 → 결과 → 타이틀을 한 바퀴 돈 뒤, 매니저 오브젝트가 종류별로
  하나씩만 존재해야 한다.
- 로그 검사: 전이 한 건마다 `[시각] [이벤트ID] [반응요약]` 형식의 줄이 하나씩 남아야 한다 [source: reference/unity_project_baseline.md 3절 로그 규칙].
- 콘솔 검사: 한 바퀴 순회 동안 콘솔 에러 0개 [source: reference/unity_project_baseline.md 4절 자체 점검].
- 상시 씬 검사: 플레이 구간 내내 World_Base가 로드된 상태로 유지되어야 한다.
- 중복 요청 검사: 로딩 중 전이 버튼을 연타해도 최종 활성 씬이 하나여야 한다.

## Synergy
- ARCH-011 (Boot 부트스트랩 & 매니저 수명): 이 구조의 출발점. 부트스트랩이 없으면 전이할
  주체 자체가 매번 새로 생긴다.
- ARCH-018 (게임 매니저): 상태의 소유자. 이 카드는 그 상태 변화가 화면 전환으로 이어지는
  경로를 맡는다.
- ARCH-002 (씬 스트리밍): 플레이 구간 내부의 씬 구성. 흐름은 구간 사이, 스트리밍은 구간 안이다.
- ARCH-010 (로그 규약): 전이 기록의 형식 근거.
- ARCH-001 (이벤트 버스): 전이 완료 통지 경로.
- ELEM-004 (반복 메커닉): 궁합 필수 — 반복이 핵심인 게임에서는 결과 → 플레이 재진입이 가장
  자주 지나는 길이므로, 전이 비용과 매니저 수명 처리가 곧 그 게임의 체감 리듬이 된다.
